# 05 — The sensor harness, reports, and MCP

The place's senses: independent, boring, crash-proof. The kami's
conversation must never block on a sensor.

## What exists today

- **Registry** — `sensors.json`: one entry per sensor (id, name, type,
  logger, log_file, interval, params, active).
- **Supervisors** — `sensors_boot.py`: one crash-isolated supervisor thread
  per active sensor, spawned by a systemd service.
- **Files** — each logger appends `key=value` lines to `sensors/<id>.md`
  (per-minute for pivitals, per-5-min for solarpower).
- **Digest** — `reports_reader.py` folds each sensor's **latest line** into
  natural language ("temperature: 51.8C · cpu load: 0% · ram usage: 17%")
  for the system prompt. A 1B model cannot parse 60 lines of raw log; the
  digest is the stopgap.
- **Journal** — cron 23:55 folds the day's sensor lines + turn log into one
  journal block.

## The reports pipeline (the real design)

On this hardware the conversational model reads the **latest reading**. The
intended shape (PLAN §4.4):

1. Raw logs accumulate in files (level 0).
2. A **smaller model — a Level-0 "analyst agent" — digests them into a
   periodic report** (per-sensor trends, anomalies, cross-sensor sentences).
3. The conversational model reads **only the report**, never raw lines.

On the Pi the two roles collapse into "read the latest line"; on bigger
hardware they split cleanly into a cheap summariser and an expensive
conversationalist. This is the first rung of the consolidation ladder
(chapter 06).

## Harness rules

- Loggers are idempotent and append-only; a crashed logger restarts and
  resumes.
- Sensors never write the conversation files; conversation never writes
  sensor files.
- Every file declares its units and meaning in its header (the digest reads
  them).
- `index.md` should eventually be generated by the summariser, not hand-
  maintained.

## MCP: the public API of the node

Model Context Protocol is how _external agents_ (and our own upper levels)
query the place. From the research
([research/channels-and-mcp.md](research/channels-and-mcp.md) §B):

- **Tools** (model-controlled): `get_sensor(id)` → latest reading,
  `list_sensors()`, `read_memory(category, file)`, `append_note(text)`,
  `ask(text)` → the generation handle. Fine-grained, JSON-Schema inputs,
  actionable `isError` results.
- **Resources** (application-driven): `kami://sensors/{id}`,
  `kami://memory/{category}/{file}` — read-only context for agents.
- **Annotations** on every tool: `readOnlyHint`, `idempotentHint`,
  `destructiveHint` — so an external agent can self-restrict to safe reads
  (the filesystem reference server's pattern).
- **State as handles**: MCP has no sessions — `ask()` returns an opaque
  generation id that later calls (`get_answer(id)`, `cancel(id)`) pass back,
  with a documented lifetime. This maps exactly onto our single-slot model.
- **Transport & security**: **stdio by default** on the Pi (secrets from the
  environment); HTTP only later, bound to localhost behind a reverse-proxy
  with auth — the posture Hass-MCP prescribes, because the MCP server is a
  distinct attack surface.

Order of work: the harness and MCP come **after** the interaction core is
flawless (chapter 03) — sensors feed memory, and memory feeds narrative;
none of it matters if the kami cannot hold a conversation.
